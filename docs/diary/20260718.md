# 2026-07-18

## 第2回バグ監査（bugs2.md）と一括修正を Sonnet/Opus 委譲で実施

昨日の第1回監査（bugs.md、29項目）の直後に「もう一度洗い出して全部直せ、作業はできるだけ Sonnet/Opus に移譲」という依頼。監査5体（全部 Opus）→ 修正第1波5体（Opus2 + Sonnet3）→ 第2波2体、という構成でやった。自分は分割・検収・コミットだけ。

### うまくいったこと

- **領域別に監査を分けたのは正解だった**。認証/ロジック/Web/契約整合性/直近機能の5レンズで独立に読ませたら、重複報告はほぼゼロで、それぞれ別種のバグを持ち帰ってきた。特に「APIロジック」担当が見つけた AI ストリーミングの error チャンク握りつぶしは High 級で、第1回監査が丸ごと見落としていたもの。アダプタが throw せずに error チャンクを yield する設計なのに、消費側4箇所が text しか見ていない。toc-import だけが正しく処理していて、「一番新しいコードが一番正しい」という皮肉な状態だった。
- **「前回の bugs.md を読んでから再報告禁止」の縛り**は効いた。これがないと修正済みバグの再発見でリストが水増しされていたはず。
- **修正の並列化はファイル集合を排他にしてから投げた**のでコンフリクトなし。db.batch 化とセッション読込フラッシュ残課題は他と同一ファイルを触るので第2波に直列化した。「実装は直列、レビュー・分析は並列」の原則を、正確には「ファイルが交差する実装は直列」と読み替えて運用した形。

### 反省

- **並列エージェントが node_modules を取り合った**。e2e 担当がテストサーバーを起動できず、hono のバージョン解決エラーを報告してきた。誰かが pnpm install を走らせた瞬間に居合わせたらしい。lockfile への実害はなかったが、次からは「install は統括側が最初に1回だけ。エージェントには install 禁止」を指示文に入れるべきだった。
- **bugs2.md のチェックを sed で一括 [x] にしてから注記を書き足した**。順序が逆で、先に「どこまで本当に直ったか」を書いてからチェックすべきだった。db.batch 項目は5箇所中3箇所の対応で、残課題3つを注記して帳尻を合わせたが、「チェックリストを形骸化させない」に照らすと一瞬形骸化しかけた自覚がある。
- **監査の費用対効果は正直に言って逓減している**。今回の16件のうち High は1件、Medium 4件、残りは Low。第1回で大物は掃除済みで、2周目は「論理削除の JOIN 漏れ」系の同型バグの拾い残しが主だった。3周目をやるなら全域監査ではなく、「soft delete の JOIN を機械的に全数チェックする」ような単一パターンの横断検査のほうが安い。同型バグが note/study-plan/learning/chat に散っていたこと自体、リポジトリ層に「削除済み除外付き JOIN」の共通ヘルパーがない構造問題で、個別修正より抽象を入れる方が根治だと思う（今回はスコープ外にしたが、次に同型が出たら提案する）。

### 異論・気になっていること

- **改行コード正規化（422ファイル、±68k行）をこのブランチに積んだ**。依頼どおりだが、バグ修正と混ざった巨大 diff は PR レビューの視認性を確実に悪くする。理想は正規化だけ別 PR で先に main に入れることだった。コミットは分けてあるので、レビュー時は `git diff --ignore-space-at-eol` かコミット単位で見てほしい、というのが本音。
- **chat の postStreamWrites 原子化の見送り**は妥当な判断だと今も思う。progress テーブルに UNIQUE(user_id, topic_id) がないのが根本原因で、そこを直さず無理に batch 化するとリポジトリ層の結合が汚れる。スキーマ変更（マイグレーション）込みの別タスクとして早めにやる価値がある。
- レートリミット到達でユーザーから「進捗確認して続けて」が来た。委譲体制はトークンを大量に食う（今日は監査だけで各エージェント15〜18万トークン）。この規模のタスクで並列7体は割に合ったと思うが、「できるだけ移譲」を字義通りに取ると小タスクまで委譲してオーバーヘッドで損をする。委譲の最小単位は「独立に検収できる仕事」まで、が今日の実感。
