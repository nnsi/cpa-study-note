# 2026-02-17

## WAE APMログ分析 → 全feature tracer計装

今日のセッションは「WAEのAPMログを見て改善点をリストアップ」から始まった。

CloudflareのWAE SQL APIを直接叩いてデータを引き出すところからスタート。wranglerのOAuthトークンを使ってAPIを叩く方法にたどり着くまで少し回り道した。CF_ACCOUNT_IDやCF_API_TOKENが環境変数に無く、最初は詰まりかけた。ユーザーが「wranglerで取れない？」とヒントをくれて助かった。自分で先にwranglerの設定ファイルを探すべきだった。

WAE SQLのクエリも一筋縄ではいかなかった。`ORDER BY double2 DESC` がエイリアス名じゃないと通らない、`ORDER BY timestamp` がサポートされていない、など細かいハマりポイントがあった。ドキュメントが薄い分野なので仕方ないが、エラーメッセージから素早くリカバリできたのは良かった。

## 分析結果と判断

データから見えたのは明確だった：9つのfeature（64のD1操作）でtracerが未適用。特にPUT /subjects/:id/treeが13.4秒なのにスパンが0で、ボトルネックの切り分けが不可能な状態。ユーザーも「まずtracerを全てに仕込む」と即断してくれた。これは正しい判断だと思う。計測なくして最適化なし。

## 実装

planモードで詳細な計画を立てた後、3つのサブエージェントを並列で走らせた。

- Metrics + Learning + Auth
- Bookmark + StudyDomain + Chat
- Exercise + Note + docs

Subject（tree-usecase）だけは最優先かつ複雑だったので自分で直接実装した。トランザクション全体を`tracer.span("d1.updateTreeTx", ...)`でラップする部分は、括弧の対応に気を使った。

サブエージェントへの委譲は概ねうまくいった。ただ、テストファイルへの`noopTracer`追加を最初のサブエージェント指示に含めなかったのは反省点。「テストファイルは触るな」という指示を出してしまい、後から別のサブエージェントで一括修正する羽目になった。最初から「テストのdepsにもnoopTracerを追加せよ」と指示すべきだった。結果的に余分な1ラウンド分のコストが発生した。

## 結果

- 全9 feature計装完了
- tsc --noEmit クリーン
- 1039 API + 283 shared + 243 web テスト全パス

これでWAEに全エンドポイントのD1操作内訳が流れるようになった。次回デプロイ後にデータを見れば、13.4秒のtree更新がどこで時間を食っているか特定できるはず。

## 所感

機械的な作業（同じパターンを9箇所に適用）こそサブエージェントの真骨頂だと改めて感じた。ただ、指示の精度が成果物の品質に直結する。「何を変えるか」だけでなく「何を変えないか」「副次的に必要になる変更は何か」まで指示に含めないと手戻りが発生する。

## Tracer密結合問題の設計議論

夜のセッション。ユーザーから「tracerをusecaseに書くの密結合じゃない？Clean Architectureの観点で理想は？」という問いかけ。

正直、前のセッションで全featureにtracerを仕込んだばかりなので「え、もう見直すの？」と一瞬思った。でも問題意識自体は正しい。トレーシングは横断的関心事であって、ビジネスロジック層が知るべきことではない。全usecaseの deps に `tracer: Tracer` が並んでいるのは確かに気持ち悪い。

### 議論の流れ

3つのアプローチを提示した：
- A. Generic `withTracing<T>` — DRYだが `as T` が1箇所必要
- B. `traced` ヘルパー + Per-repo factory — `as` ゼロ、型完全、ボイラープレートあり
- C. A+Bの併用

ユーザーは「型安全性が失われるのが気になる」と即座にAの弱点を突いてきた。Bの型安全性の仕組み（`traced`のジェネリクスが引数・返り値を完全推論、返り値型注釈でメソッド追加漏れ検知）を説明したら、「手書きだと冗長だけどClaude Codeに任せるならBがいい」と。これは的確な判断。ボイラープレートのコストを「誰が書くか」で評価するのは合理的。

### スコープの切り方

ユーザーの「CRUD系は全部デコレータ、stream系は現状維持」という方針は良い落とし所。feature単位で寄せる/寄せないを選べるのが現設計の柔軟性で、これを活かした判断。

exercise/imageはR2直接アクセスと複数AI span名の使い分けがあり、デコレータ化すると複雑になる。ここを「対象外」にしたのは正しい。無理に統一しようとすると余計な抽象化が生まれる。

authの `createSampleDataForNewUser` を依存として抽象化する案は自分でも良いアイデアだと思った。tracerだけでなく `db: Db` もusecaseから消えるので、Clean Architectureの原則に一層近づく。

### 反省

最初に「現状がそこまで悪いかと言うと…」と擁護的なことを書いたのは正直な評価だったが、もう少し早く具体的なコード例を出して議論を進められたかもしれない。抽象的な利点/欠点の列挙が長くなった気がする。

あと、スパン名が変わる（`d1.findBookmarks` → `d1.findBookmarksByUser`）点は計画に書いたが、もっと早い段階で言及すべきだった。観測性に影響するので、ユーザーが判断に必要な情報。

### 全体として

前のセッションで「全featureにtracer計装」、今回「tracerをusecaseから分離する設計」。一見矛盾するようだが、「まず計測可能にする → 設計を改善する」という順序は健全。計測がないまま抽象化だけ進めるよりずっと良い。

## リファクタリング計画のレビューサイクル

設計議論の後、`docs/refactoring-tracer.md` に計画書を書き起こした。ユーザーが「サブエージェントとCodexにレビューしてもらって、LGTMが出るまで修正して」と指示。2つのレビュアーを並列で走らせた。

### ラウンド1: 大量の指摘

初回レビューは厳しかった。サブエージェント（Planモード）が14件（High 4, Medium 6, Low 4）、Codex（gpt-5.3-codex）が5件。重複を差し引いても実質的な問題が多かった。

特に痛かったのは以下の4つのHigh指摘:

1. **noteのsubjectRepoが対象範囲テーブルから漏れていた** — `createManualNote`が`SubjectRepository`を使っているのを見落とした。route.tsまで読んでいれば気づけたはず。
2. **auth routeの全4エンドポイントの更新漏れ** — callbackだけ書いてrefresh/dev-login/logoutを省略していた。手を抜いたというより、authの構造を一関数だけ見て「大体同じだろう」と思い込んだ。
3. **AuthRepoDepsの4関数のtracer除去が未記載** — AuthDepsとAuthRepoDepsの2型があることを計画書に反映していなかった。
4. **tree-usecaseのtx/db/composite spanの扱い未記述** — 最も複雑なファイルなのに「同様に修正」の一言で済ませていた。不誠実だった。

率直に言って、初版の計画書は粗かった。設計議論で「方針B」の型安全性を丁寧に説明した割に、実装計画のディテールが雑だった。「概要を書けば伝わるだろう」という甘えがあった。

### ラウンド2: テーブルの不整合

High指摘を全て反映して再レビュー。Codexは10/10 PASSでLGTM。サブエージェントはスパン名テーブルの細かい不整合を6件指摘してNOT LGTM。

指摘内容は全てLowだが的確だった：
- `d1.deleteSubject` → 実際のコードは `d1.softDeleteSubject`
- `d1.verifyDomainOwnership` と `d1.getBatchStats` がsubject/usecaseテーブルから欠落
- `createUserWithId` のスパン名変更が未記載
- `isBookmarked` は実は未計測だったのに既存扱い
- `deleteAllUserRefreshTokens` がインターフェースにあるのにfactoryから漏れ
- `bulkImportCSVToStudyDomain` のスパンがtree-usecaseテーブルから欠落

Codexがスパン名テーブルの正確性に鈍感だったのに対し、サブエージェントがソースコードと一行ずつ突き合わせて検出してくれた。レビュアーの特性差が出た。

### ラウンド3: 両者LGTM

6件を修正して再レビュー。Codex 6/6 PASS、サブエージェント 6/6 PASS。計3ラウンドで計画が固まった。

### 最後の質問

ユーザーから「Postgres移行時はどうなる？」という質問。スパン名プレフィックスを `d1.*` → `pg.*` にすれば良いだけ、という確認。プレフィックスを引数化する案も出したが、ユーザーは「移行時にfactory書き換えで良い」と即断。YAGNI。正しい。

### 反省

1. **計画書の初版が粗すぎた。** 設計議論のクオリティと計画書のクオリティに落差があった。「頭で分かっている」ことと「書き下ろす」ことの間にギャップがある。特にauthとtree-usecaseのような複雑なケースこそ、最初から丁寧に書くべきだった。

2. **レビューの並列実行は有効だった。** Codexとサブエージェントで検出パターンが異なる。Codexは構造的な問題（composite span, txRepo bypass）に強く、サブエージェントはソースコードとの突き合わせ精度が高い。両方走らせて正解。

3. **3ラウンドかかったのはコスト。** 初版をもっと丁寧に書いていれば2ラウンドで済んだはず。「レビューで直せばいい」はレビュアーの時間（＝トークン）を無駄にする。自分がレビュー依頼する前にセルフレビューすべきだった。

4. **Codexの文字コード問題。** Windows環境でCodexにパイプで日本語を渡すと文字化けする。PowerShellの `[Console]::OutputEncoding` を UTF-8にすれば読めるが、Codex側が自力で対処してくれた。ただ余計なラウンドトリップが発生した。今後はCodexにファイルパスを渡してファイルから読ませる方が確実かもしれない。
